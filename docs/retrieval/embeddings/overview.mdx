Semantic search is optional in Fraise, and **the server never computes a vector.** It stores what it is given, indexes it, and searches it. Deciding what text means is the caller's job.

That split is deliberate. Embedding models change often, cost money, and differ per deployment; a database that picked one would be wrong for most callers and would tie a memory store's release cycle to a model vendor's.

## The path a vector takes

<Mermaid
  chart='flowchart TD
  src["text"] --> embedder["embedder (SDK, your process)"]
  embedder --> vector["[0.10, 0.22, ...]"]
  vector --> params["parameters: {#39;v#39;: [...]}"]
  params --> query["query: remember #39;the parrot is turquoise#39; topic:birds vec:$v"]
  query --> store["graph N: fact node + vector index entry"]'
/>

A vector reaches the server as a request **parameter**, bound to a `vec:$v` reference in the query — never inline in the query text. The query string is lexed on every call and written to the log; a few thousand floats spliced into it would bloat every log line and put the lexer to work for nothing. See [Query endpoint](/docs/http-api/endpoints/query) for the request shape.

## `vec:` on both commands

- on `remember`, the vector is the fact's embedding, stored and indexed with it;
- on `recall`, it is a semantic seed — the vector index returns its nearest neighbours, which then seed the graph walk.

## Vectors are a seed, not an answer

A vector is one seed among several: a recall may carry it alongside terms and anchors, or on its own. The vector index contributes its nearest neighbours — `seed-size` of them, or `top:` when that is larger — and the text index its own matches, each carrying its raw mass; a fact found by both adds the two. When the recall names an anchor and takes `depth:1` or `depth:2`, anchors then pass their surplus on to their facts, and the result decays by age.

<Note title="One signal, not the ranking" type="note">
  **Semantic similarity is one signal feeding a ranking, never the ranking itself.**
</Note>
