Fraise employs three mechanisms to handle concurrency:

1. **Multi-graph partitioning** — distributing data across independent in-memory graphs
2. **Worker pool scheduler** — processing streams through configurable workers
3. **Per-graph read-write locks** — protecting individual graph state

Together, these enable high-performance concurrent reads with serialized writes per graph.

## Independent graphs

The database maintains multiple independent temporal memory graphs (8 by default). Each graph is a completely separate in-memory data structure containing:

- nodes: facts, entities and topics
- text search indices
- vector (semantic) indices
- adjacency maps for graph traversal

## Graph partitioning

Streams specify a target graph via `Query.GetGraphID()`, which returns an index (0–7 by default). This partitioning allows:

- multiple writes to **different graphs** to proceed in parallel;
- reads from any graph at any time, unless a write is in progress on that graph;
- independent scaling: no global lock contention.

All graphs within a database share the same underlying configuration and lifecycle (Start/Stop).

## Isolation, not only concurrency

A graph is also an isolation boundary, not only a lock domain: no query reads across graphs, and no walk traverses between them. That is why the graph selector is validated twice, in two different layers — see [Memory graphs](/docs/retrieval/memory-model/memory-graphs), which also covers when to partition data across several.

<Note title="Isolation boundary" type="warning">

  **Concurrency is the reason to have several graphs; isolation is the reason to be careful which one a query names.**

</Note>
