## Per-graph locks

Each graph holds a `sync.RWMutex` protecting its internal state — its nodes, the adjacency maps between them, and its two indexes:

```go
type InMemoryGraph[K ~uint64, P float32 | float64] struct {
    idToNodes     map[K]Node[K] // all nodes
    nodeToSources map[K]map[K]K // incoming: target -> source -> edge
    nodeToTargets map[K]map[K]K // outgoing: source -> target -> edge

    textIndex   *index.BTreeIndex[K, P]
    vectorIndex *index.RPTreeIndex[K, P]

    // search algorithms, hasher and config elided

    mu sync.RWMutex
}
```

Public methods for lock management:

- `RLock()` / `RUnlock()` — acquire/release a read lock
- `Lock()` / `Unlock()` — acquire/release a write lock

## Lock holder responsibility

The graph interface exposes locks to allow callers to compose operations while holding a single lock:

```go
g.Lock()
defer g.Unlock()

if node := g.Get(key); node != nil { // read under the lock
    return g.Put(key, modified)      // write under the same lock
}
```

<Note title="No internal locking" type="warning">

  This prevents **read-modify-write races**. The graph's own operations take no lock: the caller holding one across the whole sequence is what makes it atomic, which is why the scheduler, not the graph, acquires it.

</Note>

## Read-write semantics

- **Reads** — multiple goroutines can read from a graph simultaneously (`RLock()`)
- **Writes** — exclusive access; blocks all readers and other writers (`Lock()`)
- **No upgrade** — a read lock cannot be upgraded to a write lock without releasing first

## Keeping hold time short

Writes commit in place, so lock hold time is proportional to the fact being written. **Keep each fact to one self-contained statement** rather than a paragraph of them — see [Concurrency guarantees](/docs/architecture/concurrency/guarantees) for the rest of the contention playbook.
