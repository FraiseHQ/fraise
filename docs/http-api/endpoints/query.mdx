Fraise exposes four endpoints: this one, [explained recall](/docs/http-api/endpoints/explain), [stats](/docs/http-api/endpoints/stats) and the [health check](/docs/http-api/endpoints/health). Everything an agent does goes through this one, and the [query language](/docs/query-language/foundations/design-principles) carries the rest.

This is the one endpoint that reads and writes. The body carries the query and any parameters it references:

```json
{
  "query": "recall bird topic:garden vec:$v top:5",
  "parameters": {"v": [0.10, 0.22, 0.87]}
}
```

| Field | Type | Required | Notes |
|--------------|------------------------|----------|-----------------------------------------|
| `query` | string | yes | one command per request |
| `parameters` | object of float arrays | no | binds `$name` references, e.g. `vec:$v` |

Vectors stay out of the query string on purpose: the query is lexed on every call and written to the log, and an inline embedding would put a few thousand floats through both — see [Parameters](/docs/query-language/tokens/parameters).

## Response

A successful recall carries ranked hits, highest score first — relevance after recency decay:

```json
{
  "results": {
    "count": 1,
    "hits": [
      {
        "value": "the parrot is turquoise",
        "timestamp": "2026-08-09T17:40:53.851+01:00",
        "score": 1
      }
    ]
  }
}
```

<Note title="Count is not a total" type="warning">

`count` is how many hits were **returned**, not how many exist — a recall is capped by `top:` and by `default-top`. How many facts a recall reaches is what a [`describe`](#a-describe-answers-with-a-catalogue) of it counts.

</Note>

### A hit carries the times its fact holds

| Field | Meaning |
|---|---|
| `value` | the fact, exactly as it was written |
| `timestamp` | when the fact was written |
| `said` | when it was said; absent when its `remember` gave no `said:` |
| `occurred` | the times what it states happened, each a `start` and an `end`; absent when its `remember` gave no `occurred:` |
| `score` | relevance after recency decay |

```json
{
  "value": "anna ran the charity race",
  "timestamp": "2026-11-12T00:53:42.421Z",
  "said": "2023-05-08T00:00:00Z",
  "occurred": [{"start": "2023-05-07T00:00:00Z", "end": "2023-05-08T00:00:00Z"}],
  "score": 2.1206
}
```

A span holds its `start` and ends just before its `end`, so the day of 7 May runs to the first instant of the 8th. One moment has the two equal, and a span that is not over has no `end`.

**An absent time was not given, and the fact reads the next one**: with no `occurred` it happened when it was said, and with no `said` it was said at its `timestamp`. Leaving the key out is what lets a client tell a time that was stated from one it falls back to. See [Temporality](/docs/retrieval/memory-model/temporality).

### A `when` answers with a time

A `when` returns the same shape, with the time it answers with as `start` and `end` on `results`, beside the hits that time was read from:

```json
{
  "results": {
    "count": 1,
    "hits": ["..."],
    "start": "2023-05-07T00:00:00Z",
    "end": "2023-05-08T00:00:00Z"
  }
}
```

The two are a span like any other: equal for one moment, and with no `end` for an answer that is not over. A `when` that matched no fact has neither, and says so in a warning. See [Commands](/docs/query-language/foundations/commands).

### A `describe` answers with a catalogue

A `describe` returns the same envelope with no hits: `count` is 0 and `hits` is `[]`, since it returns no fact, and `catalogue` on `results` carries the shape of every fact its recall reaches:

```json
{
  "results": {
    "count": 0,
    "hits": [],
    "catalogue": {
      "graph": 0,
      "scope": "topic:sailing top:2",
      "facts": 3,
      "anchors": 4,
      "happened": {"start": "2023-05-01T00:00:00Z"},
      "said": {"start": "2023-06-02T00:00:00Z", "end": "2023-07-03T00:00:00.000001Z"},
      "written": {"start": "2026-11-15T13:37:18.187508Z", "end": "2026-11-15T13:37:18.217466Z"},
      "topics": [
        {"value": "sailing", "facts": 3, "happened": {"start": "2023-05-01T00:00:00Z"}, "said": {"start": "2023-06-02T00:00:00Z", "end": "2023-07-03T00:00:00.000001Z"}, "written": {"start": "2026-11-15T13:37:18.187508Z", "end": "2026-11-15T13:37:18.217466Z"}}
      ],
      "entities": [
        {"value": "anna", "facts": 3, "happened": {"start": "2023-05-01T00:00:00Z"}, "said": {"start": "2023-06-02T00:00:00Z", "end": "2023-07-03T00:00:00.000001Z"}, "written": {"start": "2026-11-15T13:37:18.187508Z", "end": "2026-11-15T13:37:18.217466Z"}},
        {"value": "east quay", "facts": 1, "happened": {"start": "2023-05-20T00:00:00Z"}, "said": {"start": "2023-06-02T00:00:00Z", "end": "2023-06-02T00:00:00Z"}, "written": {"start": "2026-11-15T13:37:18.201439Z", "end": "2026-11-15T13:37:18.201439Z"}}
      ]
    }
  }
}
```

| Field | Meaning |
|---|---|
| `graph` | the graph described, the one the recall's selector names |
| `scope` | the recall's body as the server read it: terms and anchors folded to lower case, clauses in one fixed order; empty for the whole graph |
| `facts` | how many facts the recall reaches: every candidate it would rank, not its first `top:` |
| `anchors` | how many topics and entities those facts are filed under, before the lists are capped |
| `happened` | from the earliest start to the latest end of what the facts state took place; no `end` when one of them is not over |
| `said`, `written` | from the first fact said, or written, to the last |
| `topics`, `entities` | the anchors the facts are filed under, the most filed first and ties by value, at most `top:` of each kind; each has its `value`, the `facts` filed under it and the three times of those facts |

A span's `end` lies outside it, so a span whose last fact holds a single moment ends a microsecond past that moment, the finest step every client reads back. A fact given no time on a clock reads the next one, as a bound reads it, so a set written with no times reads the same on all three. The times are left out when the recall reached no fact, while `topics` and `entities` are always there, `[]` when there is none. Under a describe of one anchor, every other anchor counts the facts it shares with the one named. See [Commands](/docs/query-language/foundations/commands).

### A write is acknowledged, not answered with results

A write has no result set. It returns 200 with an acknowledgement of its own:

```json
{"status": "ok"}
```

The `status` key is what tells a write apart from a read. It is a fixed token rather than a message — treat its presence, not its wording, as the signal that the fact was stored.

### An empty graph answers 204

A recall or a `describe` of a graph that holds nothing comes back `204 No Content`, with no body at all. It is a success, not an error: there was nothing to search.

This is deliberately distinct from a recall that searched a populated graph and matched none of it, which stays 200 with an empty result set:

```json
{"results": {"count": 0, "hits": []}}
```

A `describe` that reached no fact of a populated graph stays 200 the same way, with a catalogue that counts none:

```json
{"results": {"count": 0, "hits": [], "catalogue": {"graph": 0, "scope": "zebra", "facts": 0, "anchors": 0, "topics": [], "entities": []}}}
```

The two call for different responses from the caller. A 204 says no fact has ever been written to this graph, so no rephrasing of the query would have helped; a 200 with no hits says the facts are there and the query missed them. Collapsing them sends a caller debugging a question when it should be checking whether it ever wrote.

A 204 carries no `warnings` either, since it carries no body — what a phrasing might have meant instead does not matter when there was nothing to search either way.

## Warnings

A query that ran but carries something it should not, such as a mis-cased keyword, a stop word among its terms or a `when` that no fact answers, has a `warnings` array beside its results, or beside a write's `status`. The key is absent when there is nothing to say, so a clean response shape is unchanged. See [Warnings](/docs/query-language/reference/warnings).

## Errors

Client errors are precise on purpose: the caller is usually a model, and a model can correct itself from a precise message. See [Errors](/docs/http-api/errors).
