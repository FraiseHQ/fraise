Fraise exposes four endpoints: this one, [explained recall](/docs/http-api/endpoints/explain), [stats](/docs/http-api/endpoints/stats) and the [health check](/docs/http-api/endpoints/health). Everything an agent does goes through this one, and the [query language](/docs/query-language/foundations/design-principles) carries the rest.

This is the one endpoint that reads and writes. The body carries the query and any parameters it references:

```json
{
  "query": "recall bird topic:garden vec:$v top:5",
  "parameters": {"v": [0.10, 0.22, 0.87]}
}
```

| Field | Type | Required | Notes |
|--------------|------------------------|----------|-----------------------------------------|
| `query` | string | yes | one command per request |
| `parameters` | object of float arrays | no | binds `$name` references, e.g. `vec:$v` |

Vectors stay out of the query string on purpose: the query is lexed on every call and written to the log, and an inline embedding would put a few thousand floats through both — see [Parameters](/docs/query-language/tokens/parameters).

## Response

A successful recall carries ranked hits, highest score first — relevance after recency decay:

```json
{
  "results": {
    "count": 1,
    "hits": [
      {
        "value": "the parrot is turquoise",
        "timestamp": "2026-08-09T17:40:53.851+01:00",
        "score": 1
      }
    ]
  }
}
```

<Note title="Count is not a total" type="warning">

`count` is how many hits were **returned**, not how many exist — a recall is capped by `top:` and by `default-top`.

</Note>

### A group hit

With [`db.aggregate`](/docs/configuration/reference/database#dbaggregate) set to `group`, off by default, a recall whose matches spread across many sessions at similar scores, an aggregation question, folds the candidates that matched by the same rare term into one hit:

```json
{
  "kind": "group",
  "key": "tournament",
  "value": "won the regional tournament last week",
  "timestamp": "2026-08-09T17:40:53.851+01:00",
  "score": 2.31,
  "count": 9,
  "members": [
    {"value": "won the regional tournament last week", "timestamp": "2026-08-09T17:40:53.851+01:00", "score": 2.31},
    {"value": "entered another tournament in may", "timestamp": "2026-05-02T11:03:10.000+01:00", "score": 1.87}
  ]
}
```

`members` are the group's facts, best first, each in the shape of a fact hit; `key` is the term they share and `count` how many there are. The group's own `value`, `timestamp` and `score` are its best member's, so a client that reads every hit as a fact still reads a true one. A fact hit carries none of these keys, and the top-level `count` counts a group as one hit. A group sits where its first member would have: a better fact still comes before it.

### A write is acknowledged, not answered with results

A write has no result set. It returns 200 with an acknowledgement of its own:

```json
{"status": "ok"}
```

The `status` key is what tells a write apart from a read. It is a fixed token rather than a message — treat its presence, not its wording, as the signal that the fact was stored.

### An empty graph answers 204

A recall of a graph that holds nothing comes back `204 No Content`, with no body at all. It is a success, not an error: there was nothing to search.

This is deliberately distinct from a recall that searched a populated graph and matched none of it, which stays 200 with an empty result set:

```json
{"results": {"count": 0, "hits": []}}
```

The two call for different responses from the caller. A 204 says no fact has ever been written to this graph, so no rephrasing of the query would have helped; a 200 with no hits says the facts are there and the query missed them. Collapsing them sends a caller debugging a question when it should be checking whether it ever wrote.

A 204 carries no `warnings` either, since it carries no body — what a phrasing might have meant instead does not matter when there was nothing to search either way.

## Warnings

A query that ran but carries something it should not, such as a mis-cased keyword or a stop word among its terms, has a `warnings` array beside its results, or beside a write's `status`. The key is absent when there is nothing to say, so a clean response shape is unchanged. See [Warnings](/docs/query-language/reference/warnings).

## Errors

Client errors are precise on purpose: the caller is usually a model, and a model can correct itself from a precise message. See [Errors](/docs/http-api/errors).
