Every failure returns the same shape, with the status code carrying the category:

```json
{"error": "parse error at column 28: \"topic\" is missing its ':': write topic:food"}
```

| Status | When |
|--------|---------------------------------------------------------------------------------------------------------------------------------------|
| 400 | malformed JSON, a body over `max-body-bytes`, an unparseable query, a missing parameter, a `top`, `depth` or vector length outside its bounds, a vector whose dimension does not match its graph, a graph selector outside the allocated range, an `explain` prefix out of place, a write sent to the deprecated `/api/v1/explain` alias |
| 404 | no endpoint answers that method and path — the message names both |
| 429 | the scheduler queue the query waits on stayed full past `enqueue-timeout` — back off and retry |
| 503 | the server is shutting down |
| 500 | an internal failure |

## Two deliberate properties

**A client error says exactly what is wrong**, including the column a parse failed at and the values a field accepts. The caller is usually a model, and a model can correct itself from a precise message, which is why the parser refuses to guess.

**A 500 never carries detail.** The body is a generic message and the specifics go to the log, so an internal error cannot leak the shape of the store to a client.

## Handling a 429

A 429 means the queue stayed full for `enqueue-timeout` and the request was shed. That is working as intended — the alternative is unbounded blocked goroutines. Back off and retry; if they are sustained, the scheduler settings are mismatched to the load. See [Load and backpressure](/docs/operations/runbook/backpressure).

## Handling a 400

The message names the fix. Common cases:

| Message names | Fix |
|---|---|
| a column and an unexpected token | correct the syntax at that column — see [Grammar](/docs/query-language/reference/grammar) |
| a range | the value exceeded a [bound](/docs/query-language/tokens/bounds) |
| a missing parameter | bind it in the request's `parameters` object |
| a dimension mismatch | the graph was built with a different embedding model — see [Dimensions](/docs/retrieval/embeddings/dimensions) |
| the graphs that exist | the selector named an unallocated graph; raise `num-graphs` or pick another |

### A reserved word as a search term

Any of `recall`, `remember`, `when`, `forget`, `update`, `explain`, `describe`, `topic`, `entity`, `since`, `until`, `top`, `depth`, `said`, `occurred`, `vec`, in any casing, is syntax wherever a search term stands. `recall since 7d` is one `:` away from `recall since:7d`, and running either reading would answer a question the caller may not have asked, so it is an error naming both repairs, spelled with the word written after the keyword:

```json
{"error": "parse error at column 12: term \"since\" is also a keyword: write since:7d if a filter was meant, or quote it ('since') to search the word"}
```

| query | the message names |
|--------------------|------------------------------------------------------|
| `recall since 7d` | `since:7d` for a time bound, or `'since'` to search the word |
| `recall top` | `top:<value>`, or `'top'`: nothing follows, so the value is a placeholder |
| `recall Top shelf` | the same two repairs, and the casing |
| `recall recall`, `recall when` | only the quote: a command has no clause reading |
| `recall explain` | only the quote: a prefix has no clause reading either |
| `recall what she said` | only the quote: `said:` and `occurred:` are clauses of a `remember`, with no reading in a search |

Once a clause has started, a keyword without its `:` has one reading left, so the message names only the clause: `recall zebras since:7d topic food` answers `write topic:food`. See [Keywords](/docs/query-language/tokens/keywords).

### A prefix out of place

`explain` stands at the head of a statement, before a recall, and is followed by whitespace, as a command word is. Anywhere else it is an error at the token it blames, and the message names the repair:

```json
{"error": "parse error at column 16: \"remember\" has no ranking to explain: the explain prefix stands only before recall — drop the prefix"}
```

| query | the message names |
|--------------------------|------------------------------------------------------|
| `explain` | the recall that must follow: `explain recall <terms>` |
| `explain remember 'x'` | the command: only a recall has a ranking to explain, so drop the prefix |
| `explain when race` | the `when`: it answers with a time and has no ranking to explain, so drop the prefix |
| `explain explain recall x` | the second prefix: a statement takes one |
| `explain@2 recall x` | the selector, which is glued to the verb: `explain recall@2` |
| `explain:recall x` | the whitespace the prefix needs after it |
| `explain x` | the word standing where `recall` belongs |
| `recall anna until:(explain recall race)` | the `when` a time bound's parentheses hold: `until:(when <terms>)` |

`describe` is reserved as a prefix but not accepted, so `describe recall x` opens with no command at all and answers `expected a command (recall, remember, when), found "describe"` (see the grammar's [Status](/docs/query-language/reference/grammar#status)). See [Explained recall](/docs/http-api/endpoints/explain) for what the prefix does.

### A recall that cannot match

Stored facts never contain English stop words, so a recall whose every search term is one, and that carries no phrase and no vector, can match nothing. That is an error rather than an empty result that reads like a miss, and a named anchor does not change it: `recall the topic:birds` is meant as `recall topic:birds`.

```json
{"error": "parse error at column 10: term \"the\" is a stop word and the only search term: stored facts never contain it, so nothing can match; give a term that is not a stop word, a phrase, or a vector"}
```

A stop word beside a term that can match is only a [warning](/docs/query-language/reference/warnings): `recall the parrot` runs as a search for "parrot".
