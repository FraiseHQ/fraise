| Setting | Flag | Default | Meaning |
|------------------------|-------------------------|-----------|-----------------------------------------------------------|
| `precision` | `-precision` | `float32` | float width of embeddings and scores: `float32` `float64` |
| `num-graphs` | `-num-graphs` | `8` | independent graphs allocated, in `[1, 256]`; selectors are `0..n-1` |
| `default-top` | `-default-top` | `10` | results returned when a recall omits `top:` |
| `default-depth` | `-default-depth` | `0` | retrieval lane when a recall omits `depth:` (0 = floor) |
| `max-top` | `-max-top` | `1000` | ceiling on `top:`, rejected at parse time past it; `0` takes the default, and the server refuses to start on a negative value |
| `max-depth` | `-max-depth` | `2` | ceiling on `depth:`, in `[0, 2]` (lanes are 0, 1 and 2); the server refuses to start on a value outside it |
| `max-vector-dimension` | `-max-vector-dimension` | `4096` | ceiling on a bound vector's length |
| `seed-size` | `-seed-size` | `10` | minimum candidate budget per source; widened to `top:` |
| `min-score-ratio` | `-min-score-ratio` | `0` | score cutoff: drop hits whose relevance is under this fraction of the best hit's, in `[0, 1]`; `0` is off |
| `window-gamma` | `-window-gamma` | `0.3` | window: the share of its temporal neighbours' matches a fact borrows when scored, at most `1`; negative is off, `0` is the default |

```toml
[db]
precision = "float64"
default-top = 10
default-depth = 2
seed-size = 64
```

## Precision is a compile-time type parameter

Both instantiations are built into the binary and this setting picks which one runs. `float32` halves the memory of every vector and score, and its precision is finer than the noise in embedding models; choose `float64` only with a reason to.

## Ceilings versus defaults

The three ceilings exist so **one query cannot force unbounded work**. They bound what a *client* may ask for; the defaults are what it gets when it asks for nothing. A value past a ceiling is rejected with the range in the message — see [Bounds](/docs/query-language/tokens/bounds).

## Score cutoff

A recall fills its list to `top:` by default, and the tail of a filled list — hits scoring a tenth of the first — rarely holds the answer but costs the model context tokens all the same. `min-score-ratio` makes the list stop where the evidence does: after ranking, any hit whose relevance is below the ratio times the best relevance in the ranked list is dropped. The ratio is a fraction in `[0, 1]`, and the server refuses to start on a value outside it. The scores and their order are untouched; only the list is shorter. A ratio is scale-free, so the same setting means the same thing whatever units the scorer produces.

Relevance here is what the evidence says about a hit, before [recency decay](/docs/retrieval/memory-model/temporality) and the ranking boost scale it into the score the list is ordered by. Decay still ranks an older fact below a newer one with the same evidence, but it never pushes it under the bar: two facts with the same evidence both clear a ratio or both miss it, whatever their age. The score a hit carries in the response is the decayed one, so a kept hit can show a score below the ratio times the first hit's, and the hit ranked first is cut like any other when its evidence is far below the best's.

The hit with the best relevance always clears its own bar, so a result that matched is shortened, never emptied; `top:` still caps it from above.

```toml
[db]
min-score-ratio = 0.3
```

The cutoff is **off by default** because the trade is yours to make: it buys precision with a little recall. [`/explain`](/docs/http-api/endpoints/explain) breaks a hit down into the contributions its relevance is folded from.

## Window

Two facts written one after the other under the same anchor are usually one exchange, a question and its answer, a statement and its follow-up, and scored one by one each is a fragment of it: the turn holding the question's words and the turn holding the answer's split the query between them and neither covers it. `window-gamma` lets a fact borrow that share of each of its temporal neighbours' term counts and length when the text index scores it, so the exchange matches as a whole. A fact that holds none of a query term but sits beside one that does becomes a candidate too, worth `gamma` of an own match. Neighbours are the facts written just before and after under a shared anchor, in write order, not in time alone: a fact under another topic borrows nothing however close its timestamp.

```toml
[db]
window-gamma = 0.3
```

The window is **on by default** at `0.3`, the operating point measured on LoCoMo (one graph per conversation, every turn under its conversation and session topics, keywords only): F1@10 from 0.378 to 0.502, precision@10 from 0.257 to 0.377, single-hop turn recall@10 from 0.704 to 0.813 and adversarial from 0.726 to 0.830, against session recall@10 from 0.899 to 0.881, since the slots a neighbour takes come from other sessions. A read costs about twice as long, the neighbours' postings being merged per term. A negative value turns the window off, as a negative half-life turns decay off, and `0` means the default; the server refuses to start on a value past 1, where a neighbour would outweigh the fact itself.

## `[db.aggregate]`

| Setting | Flag | Default | Meaning |
|--------------|-------------------------|----------|-------------------------------------------------------------|
| `name` | `-aggregate` | `spread` | `spread` folds candidates that matched by the same rare term into group hits when the gate below clears; `none` returns facts only |
| `pool` | `-aggregate-pool` | `60` | ranked candidates the grouping considers, from the top |
| `spread` | `-aggregate-spread` | `4` | the gate: distinct facets the top of the ranking must span before grouping runs |
| `ratio` | `-aggregate-ratio` | `0.5` | share of the best score a candidate needs to count towards the spread, in `[0, 1]` |
| `min-size` | `-aggregate-min-size` | `3` | smallest cluster returned as one group hit, at least 2 |
| `max-groups` | `-aggregate-max-groups` | `2` | most group hits one recall returns |

```toml
[db.aggregate]
name = "none"
```

An aggregation question, "how many tournaments has Nate entered", "what types of yoga has Maria practiced", has one piece of evidence per session, and ten slots cannot hold nine sessions when the best session's neighbouring turns fill the top of the list. A group hit can: one slot carrying every fact that matched the query by the same rare term, its members best first, and the slots it frees go to the next best facts. In the response a group is marked `"kind": "group"`, carries its `key` term, a `count` and its `members`, each in the wire form of a fact hit; its own `value`, `timestamp` and `score` are its best member's, so a client that reads every hit as a fact still reads something true. A fact hit carries none of those keys, so the wire form a client knew before groups existed is unchanged.

The gate is the result's **spread**: how many distinct facets the first twenty candidates scoring at least `ratio` of the best belong to. A facet is the finest anchor a candidate is filed under beyond the anchors the query named, since those are shared by every candidate and say nothing: on a graph filed by session it is the session, and a candidate under no other anchor is its own facet. A specific question peaks on one or two facets and is returned as facts; an aggregation question is flat across many and is grouped. [`/explain`](/docs/http-api/endpoints/explain) reports the spread the gate read as `spread` on the result. Grouping needs a term to group by, so a recall with no keywords, a vector or an anchor alone, is never grouped.

Grouping is **on by default** at the thresholds above, measured on LoCoMo (same protocol as the window's); `name = "none"` turns it off: session recall@10 from 0.899 to 0.945, recall@1 from 0.648 to 0.758, precision@10 from 0.257 to 0.311 and F1@10 from 0.378 to 0.437; by category at k = 10, multi-hop from 0.671 to 0.817, open-domain from 0.637 to 0.782, single-hop from 0.966 to 0.985 and adversarial from 0.975 to 0.993, with a group hit on 946 of the 1,982 questions averaging 25 members. With the window at 0.3 as well: recall@10 0.931, precision@10 0.404, F1@10 0.539, recall@1 0.775, multi-hop 0.751, open-domain 0.741, single-hop turn recall 0.858. The `pool` is the size of the answer to an aggregation question as much as a cost, so raise it with care: a group of sixty members is sixty facts in one slot.

## `num-graphs`

Graphs are allocated at startup and the count never grows: a selector is an index, not a lookup. A selector is a `uint8`, so `256` graphs is every selector a query can name, and startup refuses a count past it rather than allocate graphs nothing can reach. Empty graphs cost almost nothing, so allocate for the isolation you want, not the load you have. See [Memory graphs](/docs/retrieval/memory-model/memory-graphs).

## `[db.hashing-function]`

| Setting | Flag | Default | Accepts |
|---------|--------------------------|----------|-----------------|
| `name` | `-hashing-function` | `xxhash` | `xxhash` `t1ha` |
| `seed` | `-hashing-function-seed` | `0` | any `uint64` |

```toml
[db.hashing-function]
name = "xxhash"
```

This derives node keys from values.

<Note title="Changing hash settings" type="warning">

  Changing either means the same fact hashes to a different key; [Durability](/docs/operations/durability) explains why that is only a concern across a restart.

</Note>
