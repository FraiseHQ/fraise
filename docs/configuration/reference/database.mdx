| `seed-size` | `-seed-size` | `10` | minimum candidate budget per source; widened to `top:` |
| `min-score-ratio` | `-min-score-ratio` | `0` | score cutoff: drop hits whose relevance is under this fraction of the best hit's, in `[0, 1]`; `0` is off |
| `window-gamma` | `-window-gamma` | `0.3` | window: the share of its temporal neighbours' matches a fact borrows when scored, at most `1`; negative is off, `0` is the default |

```toml
[db]
precision = "float64"
default-top = 10
default-depth = 2
seed-size = 64
```

## Precision is a compile-time type parameter

Both instantiations are built into the binary and this setting picks which one runs. `float32` halves the memory of every vector and score, and its precision is finer than the noise in embedding models; choose `float64` only with a reason to.

## Ceilings versus defaults

The three ceilings exist so **one query cannot force unbounded work**. They bound what a *client* may ask for; the defaults are what it gets when it asks for nothing. A value past a ceiling is rejected with the range in the message — see [Bounds](/docs/query-language/tokens/bounds).

## Score cutoff

A recall fills its list to `top:` by default, and the tail of a filled list — hits scoring a tenth of the first — rarely holds the answer but costs the model context tokens all the same. `min-score-ratio` makes the list stop where the evidence does: after ranking, any hit whose relevance is below the ratio times the best relevance in the ranked list is dropped. The ratio is a fraction in `[0, 1]`, and the server refuses to start on a value outside it. The scores and their order are untouched; only the list is shorter. A ratio is scale-free, so the same setting means the same thing whatever units the scorer produces.

Relevance here is what the evidence says about a hit, before [recency decay](/docs/retrieval/memory-model/temporality) scales it into the score the list is ordered by. Decay still ranks an older fact below a newer one with the same evidence, but it never pushes it under the bar: two facts with the same evidence both clear a ratio or both miss it, whatever their age. The score a hit carries in the response is the decayed one, so a kept hit can show a score below the ratio times the first hit's, and the hit ranked first is cut like any other when its evidence is far below the best's.

The hit with the best relevance always clears its own bar, so a result that matched is shortened, never emptied; `top:` still caps it from above.

```toml
[db]
min-score-ratio = 0.3
```

The cutoff is **off by default** because the trade is yours to make: it buys precision with a little recall. [`/explain`](/docs/http-api/endpoints/explain) breaks a hit down into the contributions its relevance is folded from.

## Window

Two facts written one after the other under the same anchor are usually one exchange, a question and its answer, a statement and its follow-up, and scored one by one each is a fragment of it: the turn holding the question's words and the turn holding the answer's split the query between them and neither covers it. `window-gamma` lets a fact borrow that share of each of its temporal neighbours' term counts and length when the text index scores it, so the exchange matches as a whole. A fact that holds none of a query term but sits beside one that does becomes a candidate too, worth `gamma` of an own match. Neighbours are the facts written just before and after under a shared anchor, in write order, not in time alone: a fact under another topic borrows nothing however close its timestamp. A fact outside the recall's time range neither lends nor borrows.

```toml
[db]
window-gamma = 0.3
```

The window is **on by default** at `0.3`. An exchange that matches as a whole ranks above its fragments, so the first hits are more often the right ones, and its turns can take several slots in one session. A read costs more with the window on, in proportion to how many facts match, since every match lends its counts to its neighbours term by term. A negative value turns the window off, as a negative half-life turns decay off, and `0` means the default; the server refuses to start on a value past 1, where a neighbour would outweigh the fact itself.

## Vector weight

A recall with both words and an embedding sums the two lanes, and when the words answer the question the text index should lead. When they do not, when the question is phrased in words the memory never used, the text index still returns its best partial matches and their mass competes with the embedding's on equal terms. So the vector similarity of every candidate is weighted by the information the text did not find:

$$
w_v = \frac{I_q}{I_{\text{hit}}} = 1 + \frac{I_q - I_{\text{hit}}}{I_{\text{hit}}}, \qquad I(S) = \sum_{t \in S} -\log_2 \frac{\text{df}_t}{N}
$$

where $I_q$ is the information in the query's words, $I_{\text{hit}}$ the part of it the best text hit holds, the best among those the recall can return, inside its time range, $\text{df}_t$ the number of facts holding word $t$ and $N$ the number of facts. A word's information is its surprisal, the bits of the event that a fact picked at random holds it: a rare word carries many bits, a word every fact holds carries none. Words no fact holds have no estimate and are left out of both sums.

The weight is the bits the text missed per bit it found, plus one. A best hit holding every word of the query leaves the embedding at its plain similarity, breaking ties; a hit holding half the query's information doubles it, a quarter quadruples it, and the embedding, which does not need the words, carries the ranking. Being a ratio of information, it reads the same for a long question as for a short one, and it has no setting: there is no constant to tune. A full match elsewhere in the graph says nothing about what the words found for this recall, so it is not the best hit; a recall with no text hit it can return keeps the embedding at weight 1. The weight is one number per query, so the vector lane's own order is kept and only its mass against the text's moves; a recall without both words and a vector is unaffected.

## `num-graphs`

Graphs are allocated at startup and the count never grows: a selector is an index, not a lookup. A selector is a `uint8`, so `256` graphs is every selector a query can name, and startup refuses a count past it rather than allocate graphs nothing can reach. Empty graphs cost almost nothing, so allocate for the isolation you want, not the load you have. See [Memory graphs](/docs/retrieval/memory-model/memory-graphs).

## `[db.hashing-function]`

| Setting | Flag | Default | Accepts |
|---------|--------------------------|----------|-----------------|
| `name` | `-hashing-function` | `xxhash` | `xxhash` `t1ha` |
| `seed` | `-hashing-function-seed` | `0` | any `uint64` |

```toml
[db.hashing-function]
name = "xxhash"
```

This derives node keys from values.

<Note title="Changing hash settings" type="warning">

  Changing either means the same fact hashes to a different key; [Durability](/docs/operations/durability) explains why that is only a concern across a restart.

</Note>
