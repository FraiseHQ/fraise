| Setting | Flag | Default | Meaning |
|------------------------|-------------------------|-----------|-----------------------------------------------------------|
| `precision` | `-precision` | `float32` | float width of embeddings and scores: `float32` `float64` |
| `num-graphs` | `-num-graphs` | `8` | independent graphs allocated, in `[1, 256]`; selectors are `0..n-1` |
| `default-top` | `-default-top` | `10` | results returned when a recall omits `top:` |
| `default-depth` | `-default-depth` | `0` | retrieval lane when a recall omits `depth:` (0 = floor) |
| `max-top` | `-max-top` | `1000` | ceiling on `top:`, rejected at parse time past it; `0` takes the default, and the server refuses to start on a negative value |
| `max-depth` | `-max-depth` | `2` | ceiling on `depth:`, in `[0, 2]` (lanes are 0, 1 and 2); the server refuses to start on a value outside it |
| `max-vector-dimension` | `-max-vector-dimension` | `4096` | ceiling on a bound vector's length |
| `seed-size` | `-seed-size` | `10` | minimum candidate budget per source; widened to `top:` |

```toml
[db]
precision = "float64"
default-top = 10
default-depth = 2
seed-size = 64
```

## Precision is a compile-time type parameter

Both instantiations are built into the binary and this setting picks which one runs. `float32` halves the memory of every vector and score, and its precision is finer than the noise in embedding models; choose `float64` only with a reason to.

## Ceilings versus defaults

The three ceilings exist so **one query cannot force unbounded work**. They bound what a *client* may ask for; the defaults are what it gets when it asks for nothing. A value past a ceiling is rejected with the range in the message — see [Bounds](/docs/query-language/tokens/bounds).

## Vector weight

A recall with both words and an embedding sums the two lanes, and when the words answer the question the text index should lead. When they do not, when the question is phrased in words the memory never used, the text index still returns its best partial matches and their mass competes with the embedding's on equal terms. So the vector similarity of every candidate is weighted by the information the text did not find:

$$
w_v = \frac{I_q}{I_{\text{hit}}} = 1 + \frac{I_q - I_{\text{hit}}}{I_{\text{hit}}}, \qquad I(S) = \sum_{t \in S} -\log_2 \frac{\text{df}_t}{N}
$$

where $I_q$ is the information in the query's words, $I_{\text{hit}}$ the part of it the best text hit holds, $\text{df}_t$ the number of facts holding word $t$ and $N$ the number of facts. A word's information is its surprisal, the bits of the event that a fact picked at random holds it: a rare word carries many bits, a word every fact holds carries none. Words no fact holds have no estimate and are left out of both sums.

The weight is the bits the text missed per bit it found, plus one. A best hit holding every word of the query leaves the embedding at its plain similarity, breaking ties; a hit holding half the query's information doubles it, a quarter quadruples it, and the embedding, which does not need the words, carries the ranking. Being a ratio of information, it reads the same for a long question as for a short one, and it has no setting: there is no constant to tune. A recall with no text hit has the embedding as its only seed, at weight 1. The weight is one number per query, so the vector lane's own order is kept and only its mass against the text's moves; a recall without both words and a vector is unaffected.

## `[db.aggregate]`

| Setting | Flag | Default | Meaning |
|--------------|-------------------------|----------|-------------------------------------------------------------|
| `pool` | `-aggregate-pool` | `60` | ranked candidates a recall's slots are spread from, from the top |
| `cap` | `-aggregate-cap` | `1` | fact hits one facet takes before the next facet gets its first, at least 1 |

```toml
[db.aggregate]
cap = 2
```

A broad question, "how many tournaments has Nate entered", "what did we decide about the budget", has its evidence spread over many sessions, and ten slots down a ranking that leans on one session hold that session ten times over. So a recall spends its slots across the facets its ranking spans instead. A facet is the finest anchor a candidate is filed under beyond the anchors the query named, since those are shared by every candidate and say nothing: on a graph filed by session it is the session, and a candidate under no other anchor is its own facet. Walking down the ranking, each facet gets its best `cap` candidates before any facet gets more, and the candidates deferred follow in rank order once every facet is served, so a ranking with fewer facets than slots still fills them and a ranking on one facet comes back as it was. The best hit is always first, being the first of its facet. The spread applies in every lane: a recall seeded by a vector or by an anchor alone is spread over its facets like a keyword recall.

`cap = 1`, the default, is the recall setting: the slots reach as many sessions as the pool offers. On the ten LoCoMo conversations, one graph each, it gives session recall@10 0.932, multi-hop 0.757 and open-domain 0.712, against 0.908, 0.679 and 0.664 with the ranking taken as it is, for precision 0.117 against 0.177: a spread list names more sessions than a stacked one, each with fewer of its turns. A larger `cap` moves back towards the ranking as it is.

The spread reads each index `pool` deep rather than `top`, so the facets below the top are there to spread over. The traversal still expands from the first `max(seed-size, top)` matches of each index, so the deeper pool costs index reads, not traversals. The vector index probes in proportion to what it is asked for, so a recall seeded by a vector costs more as the pool deepens; `pool` is the dial.

## `num-graphs`

Graphs are allocated at startup and the count never grows: a selector is an index, not a lookup. A selector is a `uint8`, so `256` graphs is every selector a query can name, and startup refuses a count past it rather than allocate graphs nothing can reach. Empty graphs cost almost nothing, so allocate for the isolation you want, not the load you have. See [Memory graphs](/docs/retrieval/memory-model/memory-graphs).

## `[db.hashing-function]`

| Setting | Flag | Default | Accepts |
|---------|--------------------------|----------|-----------------|
| `name` | `-hashing-function` | `xxhash` | `xxhash` `t1ha` |
| `seed` | `-hashing-function-seed` | `0` | any `uint64` |

```toml
[db.hashing-function]
name = "xxhash"
```

This derives node keys from values.

<Note title="Changing hash settings" type="warning">

  Changing either means the same fact hashes to a different key; [Durability](/docs/operations/durability) explains why that is only a concern across a restart.

</Note>
