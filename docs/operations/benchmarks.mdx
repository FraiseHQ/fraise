title: "Benchmarks"
description: "How every change is measured for retrieval quality and latency, when a regression blocks it, and how to run the same comparison locally"
---

Every change to the server is measured against what it changes, on two axes: **retrieval quality**, how well recalls find the facts a question needs, and **latency**, how long the work takes. A change that makes either worse fails a check before it merges, and a release is measured against the release before it.

## What runs when

| When | Compared | Gates | Outcome |
|---|---|---|---|
| A pull request that touches Go | the head against its base, on one runner | microbenchmarks, retrieval quality on the LoCoMo sample, text only | a required check; Discord on a regression |
| The release pull request | the release against the previous release tag | microbenchmarks, retrieval quality seeded with embeddings | a required check; Discord always |
| Every night | `main` against the last release tag | retrieval quality seeded with embeddings, HTTP latency at ten and a hundred thousand facts | report only; a Discord digest, flagged when a gate fails |
| A push to `main` | the commit against the one recorded before it | microbenchmarks, retrieval quality on the sample | appended to the `benchmark-history` artifact; a commit comment when a value moves past its threshold |

Base and head are always measured in the same job, on the same machine: [benchdiff](https://github.com/WillAbides/benchdiff) checks the base out beside the head and runs the same benchmarks in both, after a warm-up run. A hosted runner's speed varies more from one machine to the next than the regressions worth catching, so a timing is only ever compared with one taken beside it. The history spans many machines and shows trends; it never decides a check.

The history is one JSON file in the `benchmark-history` artifact. Each push to `main` downloads the newest one, appends its results and uploads it again, so the latest run's artifact always holds every entry, latency and retrieval quality each under its own name. It is the data file [github-action-benchmark](https://github.com/benchmark-action/github-action-benchmark) keeps, so its tooling reads it as is.

## The benchmarks

They are Go benchmarks, beside the code they measure, and run as any other with `go test -bench`.

**Microbenchmarks** are the benchmarks under `internal/`: query commit, graph search in each lane and with a vector seed, both indexes, and key hashing.

**Retrieval quality** is `BenchmarkRetrievalQuality` in `pkg/server`. It starts a server, ingests the [LoCoMo](https://github.com/snap-research/locomo) conversations `FRAISE_LOCOMO` names through the HTTP API, one fact per turn exactly as the amb benchmark's raw ingestion does, and asks each question as a recall of its words scoped to its conversation, ten results deep. A result counts for the session its fact was said in, and each question scores:

| Metric | Meaning |
|---|---|
| `f1@10` | the harmonic mean of the precision and recall below, over the sessions the ten results came from |
| `p@1` | whether the first result's session holds the question's evidence |
| `recall@10` | the share of the evidence's sessions the ten results reach |

Each is averaged over all questions and reported per category: single-hop, multi-hop, temporal, open-domain and adversarial. These numbers are exact: the same server asked the same questions over the same facts ranks them the same way, so one run of each side is a measurement and any difference is a change in retrieval.

The sample is LoCoMo's conversation `conv-26`, in `tests/perf/data`: 199 questions across all five categories. LoCoMo is licensed CC BY-NC 4.0, not MIT like the rest of the repository; `tests/perf/data/NOTICE.md` gives the attribution.

**HTTP latency** is `BenchmarkHTTP` in `pkg/server`. It fills a fresh server with a deterministic corpus, then holds it at a constant arrival rate of mixed recalls and writes for a fixed time, and reports the p50, p95 and p99 of the responses. Requests arrive on schedule however slowly the server answers, so the percentiles include the queueing a real client would see.

Both start the server as the binary does, on `tests/perf/fraise.config.toml`, and talk to it over HTTP, so what they measure includes everything a client waits for.

## The gates

A gate is a pytest test in `tests/perf`, one file per Go package: `server_test.py` judges `pkg/server`'s benchmarks, `graph_test.py` those of `internal/graph`, and so on. Its marker names the benchmarks and how to run them, and the test asserts its limits on the comparison it is handed:

```python
@pytest.mark.bench("./internal/graph", "BenchmarkSearch")
def test_allocations_do_not_grow(comparison):
    grown = [row for row in comparison if row.unit == "allocs/op" and row.change >= 0.05]
    assert not grown
```

Each row is one benchmark and unit of [benchstat](https://pkg.go.dev/golang.org/x/perf/cmd/benchstat)'s comparison: each side's median, and for a timed unit a Mann-Whitney U test, so a difference counts only at p < 0.05. A unit the benchmark declares exact counts any difference. benchstat names units in base units, so time per operation is `sec/op`.

| Gate | Fails when |
|---|---|
| retrieval quality | any metric, overall or in any category, drops by more than 0.001 |
| allocations | allocations per operation grow by 5% or more |
| time | time per operation grows by 25% or more, at p < 0.05 over ten runs a side; 10% warns |
| HTTP latency (nightly) | p99 grows by 25% or more, at p < 0.05 over five runs a side |

Retrieval and allocations are counted, not timed, so they need no statistics and their limits sit at the smallest change worth a look. Time is tested against the spread of its runs on each side, and only a large, significant slowdown fails: a smaller one is a warning a reviewer sees.

## Reading the report

Each comparison posts one comment on its pull request, updated on every push. It opens with the verdict, lists the gates that failed and the regressions accepted, then has a table per comparison with the base, the head and the change; `~` means the difference is within noise. The raw `go test` output of both sides is attached to the run as the `benchmarks` artifact.

## Accepting a regression

Some changes are worth what they cost: a ranking change that trades a category's `p@1` for a large gain elsewhere, or a write path that allocates more to stop walking the graph. To merge one, label the pull request `perf-regression-accepted` and add a line to its description that starts with `Perf:` and says why:

```text
Perf: single-hop p@1 drops 0.004 for +0.03 f1@10 on multi-hop; see the report.
```

Both are required. With them, every gate is expected to fail: its regressions still show in the report, as accepted, with the reason. The label alone changes nothing, so every accepted regression has its reason in the history.

## Running it locally

The gates run the same way locally as in CI:

```bash
make bench BASE=origin/main       # every pull request gate, head against BASE
make bench-nightly BASE=v0.3.0    # the nightly gates, HTTP latency included
```

Results go to `bin/perf/`: each side's raw output and `report.md`, the report CI posts. To run a benchmark on its own:

```bash
FRAISE_LOCOMO=$PWD/tests/perf/data/locomo-conv-26.json \
  go test ./pkg/server -run '^$' -bench BenchmarkRetrievalQuality -benchtime 1x
```

## Embeddings

The release gate and the nightly run seed retrieval with vectors from a cache, keyed by the sample and the embedding model. The **Embed LoCoMo** workflow fills it with `tools/embed_locomo.py`, and `make perf-vectors` does the same locally, into `bin/perf/locomo-vectors.json`; run the workflow from `main` whenever either changes. Both sides of a comparison read the same file, so they are compared on identical vectors.
