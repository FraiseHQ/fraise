The Python SDK is dependency-light and supports vector search when you supply an embedder.

`recall` takes keywords positionally, as in `recall("parrot", "turquoise")`, and a natural-language question as `query=`, sent as one quoted phrase so its words never collide with the grammar's keywords. Anchors go in `topics=` and `entities=`, the graph in `graph=` (0 by default), and `top=`, `depth=`, `since=` and `until=` map to their clauses.

## Typed helpers and raw FQL

There are two ways to send a query, and they differ in how much the SDK does for you.

`remember` and `recall` write the FQL for you and take any value. A topic or entity is sent bare when it is one plain word — letters and digits only — and quoted when it holds anything else, so `topics=["US elections"]`, `topics=["machine-learning"]` and `entities=["O'Brien"]` all work; a reserved word is an ordinary anchor, since after the `:` only a value can appear. A keyword follows the same rule, so `recall("e-mail")` and `recall("new york")` search for exactly those words. A keyword that spells a [reserved word](/docs/query-language/tokens/keywords) is quoted too, and warns with a `FraiseWarning`: `recall("since", "7d")` searches for the word "since", though it may have been meant as a `since:7d` bound, which only `query` can send. An argument no query can carry — an empty value, a graph outside 0–255 — raises `FraiseQueryError` before anything is sent.

```python
client.recall("since", "7d", topics=["US elections"])
# FraiseWarning: keyword "since" is a reserved word, so it was searched as the
# word 'since'; to use it as FQL syntax, write the query with client.query
# sends: recall@0 'since' 7d topic:'US elections'
```

`query` sends the FQL you wrote, exactly as written: nothing is quoted or checked on the way out. It is the route for everything the typed helpers do not cover, such as a bound counted back from now or a `when` asked on its own. When the server rejects a query, the error comes back as `FraiseAPIError` carrying the server's message, which names the fix.

```python
client.query("recall@0 ferry since:7d")
client.query("when 'charity race'")
```

See [Identifiers](/docs/query-language/tokens/identifiers) for what counts as a plain word.

## Dating a fact, and bounding a recall by time

```python
from datetime import date

from fraise_sdk import FraiseClient, When

client = FraiseClient("http://localhost:9876")
client.remember(
    "anna ran the charity race",
    entities=["anna"],
    said=date(2023, 5, 8),
    occurred=[date(2023, 5, 7)],
)
client.recall("anna", until=When("charity race"))                      # what happened before the race
client.recall("anna", since=date(2023, 5, 1), until=date(2023, 6, 1))  # what happened in May
```

`remember` takes `said=`, when the fact was said, and `occurred=`, a list of the times what it states happened. `recall` and `explain` take `since=` and `until=`. A time is a `date` or a `datetime`, never text; `Interval` and `When` are imported from `fraise_sdk`, beside the client. See [Temporality](/docs/retrieval/memory-model/temporality) for what each time means and which one a bound reads.

| Value | Names | Goes in |
|---|---|---|
| `date(2023, 5, 7)` | that day, read in UTC | `said=`, `occurred=`, `since=`, `until=` |
| a `datetime` | that moment, in the offset it carries | the same four |
| `Interval(start, end)` | the span between two moments, holding `start` and ending just before `end`; `end=None` for one that is not over | `occurred=` |
| `When("charity race")` | the time another fact holds | `since=`, `until=` |

A month or a year is the `Interval` from its first midnight to the first midnight after it. A `datetime` with no time zone is read as UTC, and the client says so once in a `FraiseWarning`, since nothing in the stored fact would tell which zone was meant.

`When` takes what a recall searches with (keywords, `query=`, `topics=`, `entities=`, `top=`, `depth=`) and a `clock=` of `"happened"`, `"said"` or `"written"`. The clock is the time read from its match and the time the recall compares against it, so `until=When("charity race", clock="said")` keeps what had been said before the race was told. A `When` names no graph: it reads the one its recall searches. One that matches no fact leaves the recall no bound to read, so the recall returns no hits and carries the server's warning.

The times come back on each hit: `hit.said` is a `datetime` and `hit.occurred` a list of `Interval`, each `None` on a fact that was given none, and `hit.timestamp` is when it was written.

## With embeddings

```python
from fraise_sdk import FraiseClient
from fraise_sdk.providers.openai import OpenAIEmbedder

client = FraiseClient("http://localhost:9876", embedder=OpenAIEmbedder())
client.remember("the parrot is turquoise", topics=["birds"])   # encoded for you
client.recall(query="colourful birds")                         # encoded for you
```

A client without an embedder still works: it writes and recalls without vectors, on text and graph structure alone. Per call, `embed=True` forces encoding and `embed=False` skips it, and an explicit `vector=` always wins. See [Producing vectors](/docs/retrieval/embeddings/producing-vectors).

## With an extractor

```python
from fraise_sdk import FraiseClient
from fraise_sdk.providers.openai import OpenAIExtractor

client = FraiseClient("http://localhost:9876", extractor=OpenAIExtractor())
client.remember("Anne's flight lands at Lisbon airport")   # filed under what it is about
```

An extractor reads each fact `remember` stores and returns the anchors it belongs under — a list of `Anchor(value, type)`, where `type` is `"topic"` or `"entity"` — and the fact is filed under them, after any `topics=` and `entities=` you pass; one you already gave is not repeated. The fact's text is stored verbatim: the extractor only chooses anchors, which drive the [graph walk](/docs/retrieval/ranking/depth). `OpenAIExtractor` (`fraise-sdk[openai]`) is the one that ships, with `gpt-5-mini` by default and the same instructions the published benchmark ingests with; any `callable(text, context) -> list[Anchor]`, or a subclass of `Extractor`, works too.

Each fact is read in its graph's `Context`: the three facts stored in that graph just before it (`recent`), and the fifty anchors extraction has filed most often there (`vocabulary`), spelled as the server stores them. Facts reach one another through the graph only by sharing an anchor, so this is what lets "she signed the papers" be filed under the person an earlier message named, and a subject that comes back sessions later be filed under the anchor it already has rather than a new spelling. The vocabulary counts only the anchors the extractor returns, so a label you pass that no message names, like a conversation or session id, stays out of it. The client keeps one context per graph, in its own process: a fact joins it once the server has stored it, and a new client starts every graph's context empty.

Extraction never costs a fact: if the extractor fails — an API error, or an answer it cannot read — the fact is stored under the anchors you gave, and a `FraiseWarning` names the failure. Per call, `extract=True` requires an extractor and `extract=False` skips it. `recall` never extracts.

## Telling an empty graph from a miss

`recall` always returns a `RecallResult`, even when nothing came back, so iterating or reading `.count` never has to be guarded. `bool(result)` tells you whether anything matched; `result.empty` tells you about the graph it searched:

```python
result = client.recall("parrot")
if not result:
    if result.empty:
        print("nothing has been remembered in this graph yet")
    else:
        print("facts are stored here, but none matched")
```

The server carries the distinction in the status line — 204 for a graph holding nothing — and the SDK reads it there. It is worth branching on: the first case is answered by writing something, the second by asking differently. See [the query endpoint](/docs/http-api/endpoints/query).

## Explaining a ranking

`explain` takes exactly the arguments of `recall` and sends the same query to [`/api/v1/explain`](/docs/http-api/endpoints/explain), which runs it through the same pipeline: the hits and their order are the ones `recall` returns, and each hit also carries `contributions`, the per-source sightings its score was folded from, while the result carries the query's `background` rate.

```python
result = client.explain("polly", entities=["polly"], depth=2)
for hit in result:
    print(hit.value, hit.score)
    for c in hit.contributions:
        print(" ", c.source, c.score, c.via)
print(result.background)
```

A `Contribution` has a `source` — `text`, `vector`, `graph` or `anchor` — with that source's raw `score`, the hit's `rank` in the source's own list and the `count` of seeds that funded it; a `graph` or `anchor` sighting also names the anchor it came through (`via`) and that anchor's `degree`, and a `graph` sighting through an anchor the recall named carries `named=True`. A hit whose only contribution is `graph` matched nothing itself and was reached through an anchor, which is what separates a multi-hop fact the graph reached and ranked low from one it never reached. The contributions are the ingredients of the final score, not shares of it; see [the explain endpoint](/docs/http-api/endpoints/explain) for how they fold together.

On a plain `recall` the breakdown is not asked for: each hit's `contributions` is empty and `background` is `None`. Use `recall` when the ranking is all you need, since the breakdown costs response size.

## Counting what a graph holds

`client.stats()` reads [`/api/v1/stats`](/docs/http-api/endpoints/stats) and returns one `GraphStats` per graph, in id order. Empty graphs are included, so the list's length is the server's graph count and a graph's row sits at its id.

```python
for g in client.stats():
    print(g.id, g.vertices, g.edges, g.nodes, g.vectors, g.forest_entries, g.relevance)
```

The fields are named for what they count: `vertices` is the endpoint's `order` (facts, topics and entities) and `edges` its `size` (a fact's links to its topics and entities), while `nodes`, `vectors`, `forest_entries` and `relevance` keep the endpoint's names. Unlike `health()`, `stats()` raises on failure, `FraiseError` when the server cannot be reached and `FraiseAPIError` on an error status, so an unreachable server is never read as an empty one.

## Version compatibility

`client.check_compatibility()` reads the `version` field from `GET /` and checks the server falls in the range this SDK supports: on a mismatch it warns and returns `False`, and `strict=True` raises instead. It is one request, made only when you call it, so it fits at startup. The `version` field is part of the server's contract for this reason; see [Health check](/docs/http-api/endpoints/health).

## TypeScript

Not available yet. Until it lands, TypeScript callers use [`fraise mcp`](/docs/integrations/mcp) or talk to the HTTP endpoint directly; it is two verbs over one route, so a client is a short wrapper around `fetch`. See [the HTTP API](/docs/http-api/endpoints/query).
