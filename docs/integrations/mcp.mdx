`fraise-mcp` is a stdio MCP server for a running daemon, so any MCP client can remember and recall. It exposes two tools, `recall` and `remember`, each taking one FQL statement: `recall` runs every read, a recall, a `when` or a `describe` in front of a recall, and `remember` every write. It embeds every statement's text on your machine, so retrieval is hybrid — text, graph and vector — out of the box. The model writes plain FQL; it never handles a vector. It ships on PyPI and runs with `uvx`, so there is nothing to install besides [uv](https://docs.astral.sh/uv/), and it needs no flags when the daemon runs on the same machine on its default port.

<Note title="Before you register" type="note">

Start the daemon first (`brew services start fraise`, or `systemctl --user start fraise` on Linux), then register the server with whichever coding agent you use.

</Note>

## Claude Code

```sh
claude mcp add fraise -- uvx fraise-mcp
```

That registers it for the current project; add `--scope user` to make it available in every project instead.

## Codex

```sh
codex mcp add fraise -- uvx fraise-mcp
```

Or write it into `~/.codex/config.toml` directly:

```toml title="~/.codex/config.toml"
[mcp_servers.fraise]
command = "uvx"
args = ["fraise-mcp"]
```

## OpenCode

Add it to `opencode.json` in your project root:

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "fraise": {
      "type": "local",
      "command": ["uvx", "fraise-mcp"]
    }
  }
}
```

## Any other client

```json
{
  "mcpServers": {
    "fraise": { "command": "uvx", "args": ["fraise-mcp"] }
  }
}
```

## Configuration

Every setting is a flag, and each flag falls back to an environment variable, so a client can configure the server through its command line or through its `env` block:

| Flag | Environment | Default |
| --- | --- | --- |
| `--addr` | `FRAISE_ADDR` | `http://localhost:9876` |
| `--model` | `FRAISE_EMBEDDING_MODEL` | `BAAI/bge-small-en-v1.5` |
| `--no-vectors` | `FRAISE_NO_VECTORS=1` | vectors on |

To reach a daemon somewhere else, on another port or another host, pass its address:

```sh
claude mcp add fraise -- uvx fraise-mcp --addr http://10.0.0.5:9876
```

The address carries no graph: each statement names its own with `@N`.

## Embeddings

The server embeds with [fastembed](https://qdrant.github.io/fastembed/), on ONNX Runtime and without torch. The default model, `BAAI/bge-small-en-v1.5`, gives 384-dimensional vectors; `--model` takes any text model fastembed supports. The model loads on the first statement that needs a vector, not at startup, so the server answers its client straight away. The first load downloads the model files into `~/.cache/fraise-mcp`, or `$XDG_CACHE_HOME/fraise-mcp` when `XDG_CACHE_HOME` is set, and later loads read them from there; `FASTEMBED_CACHE_PATH` names another directory.

A `remember` embeds its fact. A `recall` embeds its search terms, the words and phrases before its first clause. The server appends `vec:$v` to the statement and binds the vector beside it, so the daemon sees an ordinary hybrid query. A recall with no terms, where [anchors alone seed the search](/docs/query-language/foundations/commands), is sent as written, and so is a `describe recall`: a vector ranks every fact that holds one, so a describe that carried one would reach all of them rather than what its terms match. So is anything the server cannot read that far: the daemon checks every statement, and its error messages come back to the model as tool errors it can act on.

With a vector on every statement, a recall finds a fact by meaning, not only by its words: `favorite color` finds `my favourite colour is teal`, so the model has no spelling variants to hedge with.

The first vector written to a graph fixes that graph's dimension, so a graph keeps the model it was first written with. Pick the model before the first `remember`, and give a graph written by another embedder its own `@N`.

## The built-in bridge

The `fraise` binary carries the same two tools without the embedding: `fraise mcp` is a stdio bridge that sends each statement as written, so it searches by text and graph, and needs no Python.

```sh
claude mcp add fraise -- fraise mcp
```

It reads configuration the way the daemon does (`fraise.config.toml` in its working directory, or the file `-config` names) and forwards to 127.0.0.1 on the port that configuration gives the server, so `fraise mcp -config <file>` finds whatever `fraise -config <file>` serves. To reach a daemon somewhere else, pass `-addr http://10.0.0.5:9876`, or set it in the config file the bridge reads:

```toml
[mcp]
address = "http://10.0.0.5:9876"
```

The address carries no graph: each query names its own with `@N`.

## What a recall reads like

The `recall` tool answers with one line for each fact, best first, beside the same hits as structured content:

```text
- [said 2023-05-08, happened 2023-04] anna trained for the race (relevance 2.674)
- [said 2023-05-08, happened 2023-05-07] anna ran the charity race (relevance 1.219)
- [said 2023-06-02, happened 2023-05-01 and 2023-05-28] anna ran the harbour drills (relevance 1.130)
- [2026-11-12] anna signed up for the autumn relay (relevance 1.000)
- [said 2023-06-02, happened 2023-05-20..] anna moors the boat at the east quay (relevance 1.000)
```

**Each fact leads with its dates**: when it was said and when what it states happened, so a model can answer "when did she run" or "what had she done before she told me" from the line itself. A fact whose two dates are the same carries the one, which for a fact given no time is the day it was written. A time prints in the widest calendar unit that holds it exactly, `2023-04` for a month and `2023-05-10..2023-05-16` for a week. A fact that happened more than once has its times joined with `and`, and one that is not over ends in `..`.

A query that is a `when` leads with the time it answered with, above the fact that time was read from:

```text
when: 2023-05-07
- [said 2023-05-08, happened 2023-05-07] anna ran the charity race (relevance 2.121)
```

A query that is a `describe` reads as its catalogue: a line that spells the describe as the server read it, with how many facts its recall reached, under how many anchors, and when they happened; then its topics and its entities, the most filed first, each with when its facts happened and how many of them are filed under it:

```text
describe recall@3: 7 facts under 5 anchors, happened 2023-04-01..
topics:
- [2023-05-01..] sailing: 4 facts
- [2023-04-01..2023-05-07] running: 3 facts
entities:
- [2023-04-01..] anna: 6 facts
- [2023-04-01..] tom: 3 facts
- [2023-05-20..] east quay: 2 facts
```

That first line is a query the model can send again, so it narrows the describe to an anchor or a window by editing what it reads, and each anchor below it names a `topic:` or an `entity:` its first recall can use. A kind with no anchor reads `topics: none` or `entities: none`, since a missing list reads as one cut off. A describe whose recall reaches no fact reads as that one line, `describe recall@3 zebra: no fact reached.`, and a describe of a graph that holds nothing reads as a recall of it does, saying the graph is empty.

The structured content is the [query endpoint](/docs/http-api/endpoints/query)'s response: each hit with its `timestamp`, `said` and `occurred`, a `when` with its `start` and `end`, and a `describe` with its `catalogue`. A fact gets its dates from `said:` and `occurred:` on its `remember`; see [Temporality](/docs/retrieval/memory-model/temporality).

## What the bridge carries, and what it cannot

The server describes itself over MCP: each tool arrives with a description and a schema for its one argument — the FQL shapes, a worked example, what a score means — so a client knows what `recall` and `remember` do and how to call them without being told.

What a tool description cannot carry is the **policy**: the habit of reaching for memory unprompted, and the judgement about what is worth keeping. That belongs in the file your agent already reads — `CLAUDE.md` for Claude Code, `AGENTS.md` for Codex and OpenCode — and two habits are enough:

- **recall** before answering anything that leans on earlier decisions or preferences;
- **remember** only facts that will still matter in a later session, one self-contained fact per call, with the topics and entities that will make it findable.

See [Context engineering](/docs/getting-started/context-engineering) for why those two habits are the ones that pay.
